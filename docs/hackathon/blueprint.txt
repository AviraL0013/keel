P42: 1. Executive Summary
P43: Keel exists because leveraged trading products stop at execution while the hardest operational problem begins immediately after entry: the position has to be monitored, funded, constrained, and sometimes killed. This is particularly acute in isolated-margin systems where each position has a separate margin boundary and collateral can be manually added to the position.
P44: Perpl gives a third-party builder unusually relevant primitives: live market state, order book, trades, funding, positions, fills, account statistics, authenticated order placement, and an explicit IncreasePositionCollateral action. Perpl’s API keys can be scoped to read/trade and cannot withdraw or transfer funds out, which makes a risk-management layer materially safer to design than a general custody bot. [Sources: Perpl API repository; Perpl integrations documentation.]
P45: Agora matters because AUSD is not merely an adjacent stablecoin in the current architecture: the user-provided research identifies AUSD as Perpl mainnet collateral. Agora’s current API also exposes real-time supply metrics plus authenticated accounts, routes, and transaction history. The retail MVP should not depend on privileged mint/redeem access; it should use AUSD already onchain and reserve Agora’s institutional routes for the company-scale funding layer. The official API confirms that Metrics is public while Accounts, Routes, and Transactions are authenticated. [Sources: Agora Public API; Transactions overview; Authentication.]
P47: What Keel is not
P48: Not another mobile version of a desktop CLOB terminal.
P49: Not a generic AI trading chatbot or prediction engine.
P50: Not a policy-language/SDK project for the six-week build.
P51: Not a custodial wallet that can withdraw user funds.
P52: Not a dashboard-only analytics product that can observe risk but cannot act on it.
P53: One-sentence company definition
P54: Keel is the operating layer that manages leveraged onchain positions after the trade is placed, beginning with mobile isolated-margin Books on Perpl.

P89: 5. Decision Engine
P90: Design principle
P91: The engine is deterministic for the MVP. It consumes fresh Perpl state and user constraints, assigns a state, chooses one bounded action, and records the reason. No LLM is in the critical execution path.
P92: LIVE STATE → NORMALIZE → DERIVE RISK FEATURES → CLASSIFY STATE → APPLY USER LIMITS → EXECUTE / HOLD → VERIFY → LOG
P93: Inputs
P94: Position state: side, size, entry, collateral, leverage, liquidation information.
P95: Market state: mark/oracle/last/mid/bid/ask/open interest/volume.
P96: Order book: best levels, depth, spread, estimated exit/rescue impact.
P97: Funding: current funding event and recent funding history.
P98: Volatility: realized volatility from recent candles.
P99: Reserve: available AUSD budget and remaining defense allowance.
P100: Book constraints: floor, cap, time limit, stance, action cooldowns.
P101: Execution health: WebSocket freshness, block height, heartbeat status.
P102: Derived risk features
P104: Decision matrix
P106: Defense should be conditional
P107: Keel must never implement “if liq distance < X then add Y” as its complete logic. Before DEFEND it must answer four questions: (1) Is the position still within the user’s intended risk profile? (2) Is the market liquid enough to make the action useful? (3) Is the reserve sufficient after this action? (4) Did previous defense actually improve the Book? If any answer is no, the system transitions toward REDUCE or EXIT.

P137: 6. Risk Model & Decision Logic
P138: Important scope boundary
P139: The MVP should compute robust relative risk features rather than pretend to build a perfect liquidation predictor. Venue-specific formulas and exact liquidation behavior must be taken from Perpl’s current protocol configuration rather than re-derived from assumptions. Perpl’s public type reference exposes initial margin, maintenance margin, fee and market-state/funding fields that should be consumed from live configuration. [Source: Perpl API types reference.]
P140: Core metrics
P142: MVP scoring philosophy
P143: Avoid one opaque 0–100 score as the only output. The app may show a compact “Survival Score” for comprehension, but the underlying engine should preserve the atomic reasons: liquidation distance, funding, depth, reserve, volatility, and time. The judge demo should show both the state and its explanation.
P144: Hard safety constraints
P145: Never spend more than the Book cap.
P146: Never rescue if the required action would violate the user’s configured stance.
P147: Never execute from stale market state beyond a configured freshness window.
P148: Never allow a recovery loop to repeatedly add collateral without checking defense efficiency.
P149: Never use an API key to perform withdrawals or transfers out; Perpl documents that those actions are not permitted via API keys. [Source: Perpl integrations documentation.]
P150: Fail closed for new risk when the risk engine loses required telemetry.

P458: 25. Investor & Judge Narrative
P459: 30-second pitch
P460: Keel is a mobile risk operator for leveraged onchain positions. Every trade becomes a Book: an isolated position, an AUSD reserve, and a few simple risk limits. Keel watches live market state, funding, liquidity, and liquidation distance and decides whether to hold, defend, reduce, or exit. Perpl provides the execution primitives. AUSD is the money rail. Monad provides the settlement environment. The point is not to keep every trade alive — it is to stop users from making the wrong decision under pressure.
P461: 2-minute pitch
P462: Trading products are optimized for opening positions. The hard part starts afterward. In isolated margin, every position carries its own risk boundary; funding can worsen that boundary while the trader is away from the screen, and additional collateral can either save a defensible position or simply throw good money after bad. Keel turns the position into a Book with three user-facing controls — stance, minimum liquidation distance, and reserve cap — plus a time limit. Under the hood, a deterministic risk engine watches live mark, funding, order-book depth, volatility, reserve, and previous defense outcomes. It can call Perpl to add collateral, reduce exposure, or exit. AUSD is the capital rail, not a sponsor badge. The mobile phone becomes the control surface for a position that is otherwise easy to neglect. Over time, the same risk model can expand from one venue to many.
P463: Investor narrative
P464: The initial company is not “an app with auto-margin.” It is a wedge into margin operations. Start with Perpl’s isolated books, prove that users trust deterministic defense/refuse/exit decisions, accumulate decision/outcome data, then expand to multi-book and multi-venue risk operations. The platform narrative is earned by usage rather than assumed at launch.

TABLE 0
THE THESIS / Keel is a mobile risk operator for isolated perpetual positions. It treats each position as a Book containing capital, constraints, live telemetry, and bounded actions. Its core job is not to keep every trade alive. Its core job is to decide, deterministically, whether to HOLD, DEFEND, REDUCE, or EXIT — and execute the chosen action within the user’s limits.

TABLE 7
